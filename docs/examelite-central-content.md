# Central exam controls and question transfers

This is the first part of the revised integration. It is implemented locally and requires explicit user deployment. It does **not** complete the full in-page ExamElite authoring and exam-taking requirement.

## Confirmed product direction

Exam tools belong inside Tech4Learn's organisation navigation and domain. ExamElite remains the engine and data authority for questions, exams, attempts and marking. Neither external workspace launch links nor an iframe constitute the desired final interface. Reuse its terminology and workflow alongside the existing shared Tech4Learn form/table template.

Superadmin controls platform availability, organisation/plan entitlements, staff permissions and central content distribution. Platform availability and commercial plan configuration are separate from an organisation's enabled modules; a provider capability must not be labelled working before its adapter and interface are complete.

Central questions can be shared into selected organisations. Superadmin can also pull organisation questions into the central bank. Each operation creates an independently owned copy with provenance; it never transfers ownership or overwrites an original. Only superadmin changes central content. Student identity and programme records remain in Tech4Learn; no reverse import of ExamElite students is implied.

## Working in this change

- Superadmin can enable the organisation's Exams module using the existing versioned module settings. The toggle preserves other modules and branding. Exam permissions now enforce this module flag at the API boundary.
- The feature-control form shows saved access beside implemented tools and remaining gaps for each of the five groups. Bulk allow/restrict selections remain local until Save. Reload retrieves the current revision after a conflict; recovered drafts from an older revision are rejected. Checkbox values use the scoped controlled draft rather than independent DOM restoration. A synthetic browser check covers stale recovery, explicit bulk saving and reload. This is a feature coverage view, not the unfinished commercial plan catalogue or plan assignment system.
- Superadmin can search the central or selected organisation question bank, select up to 50 questions and share or pull them. Organisation users can view only their own question bank, with module, permission, organisation scope and question-feature checks.
- Questions are paged by stable ID, 50 at a time; search executes in ExamElite. Table filters apply to the explicitly labelled loaded collection. List snippets are escaped text, not executable provider HTML.
- Transfers validate the complete selection against the source tenant before copying. The existing additive ExamElite copy service preserves question configuration, translations and taxonomy, including numeric answer settings. Central pulls reuse existing central language identities without overwriting them.
- A per-workspace request ID makes a lost-response retry safe. A separate copy map preserves subsequent destination edits even when a new transfer request selects the same source again. Reusing a request ID with changed input is rejected.
- The ExamElite transfer table records direction, actor UUID, source/copy IDs and time. The superadmin screen exposes the latest 50 transfers. Tech4Learn also writes an audit event; remote success followed by a local audit failure can be retried safely.
- Sharing can provision an isolated exam organisation through the existing private identity bridge without issuing a launch ticket. Credentials and native session details never reach these screens.
- The organisation UI no longer displays external authoring/student launch buttons. Existing linked result reads remain available.
- Staff with exam management access can create and edit an organisation-owned question inside Tech4Learn: basic formatted text, options, answers, hints, explanations and marks. Changes invoke the installed ExamElite controller with a private mapped staff context. Native validation remains authoritative.
- Authoring uses a revision check, an atomic native transaction and a durable request ledger for safe retries. Unsupported fields cannot change ownership. The API derives the actor from the authenticated session and enforces module, organisation and question restrictions.
- Native authoring retries recheck the active organisation and mapped staff membership before returning a stored outcome. Revoking the native staff mapping therefore also blocks a retry of a previously successful save. Isolated tests verify denied retries leave content and the request ledger unchanged, and that restoring access preserves the original outcome.
- Question types, language and classification use bounded, searchable native choices scoped to the organisation. Creation captures the model from the native event dispatcher rather than guessing a latest ID. Its request ledger prevents duplicate creation on retries.
- Classification create/update reuses native controllers and the same revision/transaction/retry controls. The Subjects feature restriction is enforced separately from the Questions feature restriction. Existing subject category assignments are preserved.
- The exam builder creates and updates organisation exams using the native ExamController: type/syllabus, groups/packages/languages, schedules, timing, passing percentage and delivery flags. It lists owned exams and adds/removes selected owned questions through the native paper actions. The adapter checks the entire question selection before writing and keeps durable retry IDs. Removing a question preserves the bank record.
- Standalone exams can select an owned category and subcategory. The subcategory lookup is filtered by an authorised parent category, and changing the parent clears the prior child selection. Lookup responses from an earlier selection are ignored. Package-based exams keep native package-derived classification. Native validation rejects foreign or mismatched categories without changing the exam; local browser checks cover a delayed lookup response and the saved category fields.
- Organisations can enable an available central language and edit its local True/False labels through the native LanguageController. The enable list excludes already enabled language codes and other organisations. Re-enabling a previously disabled language preserves its native ID and resets labels from the central definition, as the native controller does. Names and codes cannot be changed through this organisation adapter, and a native platform-admin context is rejected. Durable retries do not duplicate the language. Central language administration remains unfinished. Native tests use isolated identity/configuration helpers; browser checks verify the enable and label-only payloads.
- Language disabling uses the same native organisation controller with a revision and durable request ID. It retains the language record and existing content; a repeated disable does not re-enable or delete it. The API verifies the returned language ID, revision and disabled flag before reporting success. The form locks editing after an uncertain response and permits an identical retry or reload. Native checks cover record retention, central-record denial and repeat operations; a synthetic browser check covers a lost response and retry.
- Free package details can be created and edited through the native PackageController: name, description, groups, category/subcategory, existing tags, expiry and active status. Existing linked-exam order, translations, photo references and document settings are preserved. Exam links remain managed from the exam editor, so package-detail saves do not resubmit its exam pivot. Foreign or unavailable numeric tags are rejected rather than silently removed. Native checks cover preservation, replay, foreign selections and paid-package rejection; a synthetic browser checks create selections and patch-only updates. Package images, new tag creation in the UI, paid-package management and package-specific document workflows remain unfinished.
- The editor uses the shared DraftForm and DOMPurify to sanitise native HTML. DOMPurify is added for this concrete rich-text rendering use case. TeX formula text can be edited and previewed in place with the same bounded renderer used by students. Preview never replaces the editable source with rendered markup. Native tests cover formula preservation, answer preservation and save retries; a synthetic browser check covers rendering, refreshing and source preservation. Existing image/MathML/math-field markup remains read-only and preserved; native upload and visual formula editing are still unfinished.

Existing question, option, model-answer, hint and explanation images have a separate hashed preview. The browser loads their raster bytes through a same-domain endpoint that checks organisation-wide exam permissions, module state and Questions restrictions before and after the provider call. The provider verifies the active workspace owner and that the image is still referenced by that question. Responses are bounded, uncached and audited by identifiers. Original source fields remain in the editable snapshot for patch-only preservation, but the preview never loads those storage URLs directly. Native checks cover foreign/inactive owners, restrictions, removed/unreferenced images and invalid raster data; HTTP checks cover scope, response validation and mid-request revocation. A synthetic browser check covers image rendering without enabling edits. Upload and replacement use the separate form described below.

## Image changes and remaining release work

The private `generate-document` exam action now invokes the installed native ExamDocumentController with the mapped organisation staff context. It requires an owned assigned package and an enabled assigned language; the native controller enforces translation approval and nonempty-paper rules before queueing. Existing exam revisions and the durable authoring request ledger protect retries, including revocation before replay. Isolated tests use the unmodified controller/lifecycle with fingerprint and job-dispatch doubles, covering one queued build, unchanged retry, foreign selection, missing approval, disabled language and empty paper. No real renderer or worker runs in these tests. The authenticated Tech4Learn exam-action API now forwards this action with the session-derived actor, bounded package/language IDs and exact document type. It enforces the Exams restriction and rejects malformed fields before contacting the provider. Generation controls, translation approval controls and actual generated-file verification remain unfinished.

Package forms also expose native question-paper and solution PDF visibility, title, header, footer and watermark settings. They use the same scoped revision-aware draft and patch-only save; native length validation and retry handling remain authoritative. Native tests cover every document setting, replay and rejection without partial writes; a synthetic browser check covers visibility and text payloads. This configures native documents but does not yet provide same-domain PDF generation or download.

The private approved-document adapter now reads an artifact selected by ExamElite's native document lifecycle service. It checks the source platform, active organisation, mapped staff, Exams restriction and explicit paper/package/language relationships. It preserves the native last-approved-artifact behaviour during replacement processing. Files must resolve within native PDF storage, have a PDF signature and fit the 10 MB bound; responses contain bytes and identifiers, never storage paths or external redirects. Dedicated-credential tests use the unmodified lifecycle service with synthetic records/files and cover ownership, restrictions, language availability, invalid files and missing approvals.

The authenticated Tech4Learn endpoint now serves these approved documents as same-domain PDF attachments. It derives the staff actor from the session, requires organisation-wide exam management access, enforces module and Exams restrictions before and after the provider call, limits requests and audits identifiers. It verifies the returned exam, package, language, document type, build ID, MIME, canonical base64 and PDF signature before releasing bytes. Query fields cannot override the actor or supply a path. HTTP tests cover attachment headers, foreign-organisation denial, malformed selections, invalid provider replies and membership revocation during the call. Saved exams now expose approved-paper and approved-solution downloads. Searchable selectors offer only assigned packages and languages; server validation remains authoritative. Downloads require saved settings, reject redirects and non-PDF responses, and use temporary local blob links with safe filenames. Leaving the component aborts the request. A synthetic browser check covers scoped selections, download filenames and missing-approval feedback. None selects an artifact without that package/language variant. Generation and approval inside Tech4Learn remain unfinished.

The image form also removes a selected image reference without uploading a file. Removal uses the same native revision and retry ledger, requires a hash present exactly once in the chosen field, and rejects requests mixing removal with new image bytes. Stored files are retained for other references. Native and browser tests cover reference-only removal and identical retry; HTTP tests reject missing or ambiguous operation fields.

The image-write backend and its browser form are implemented locally. It accepts one PNG/JPEG/WebP up to 512 KB and 20 million pixels for a saved owned question, with a field name and optional existing image hash to replace. It reuses ExamElite's public storage disk and native question-update controller. Workspace, active staff, revision and request-ledger checks run before writing. Repeating the request returns its prior result without storing again; a native-save exception rolls back the question and removes the new file. Replacement retains the old file because another copied question may still reference it. An abrupt process/host termination between storage and transaction completion can leave an unreferenced file; reconciliation is not implemented yet. The HTTP route validates bounded fields, derives the actor, rechecks access after the native response and audits identifiers only. Isolated native tests use a storage double and verify append, replacement, retries, invalid inputs and failure cleanup. The shared draft form offers append or replacement within a chosen question field, with a local file preview. Only destination choices enter the scoped draft; file bytes and pending request payloads stay in memory. Other question changes must be saved first. An uncertain upload freezes ordinary editing and retains the identical retry request; reload reads the saved version before another attempt. Successful writes refresh the question and private preview. Synthetic browser checks cover file-size rejection, editor locking, identical retry, draft exclusion and replacement targeting. Real deployment and representative media checks remain outstanding.

Central-original editing, the native media/formula authoring editor, the full plan/provider module catalogue, package media/paid management, central language management, OMR/PDF workflows and representative end-to-end verification remain unfinished. The current question editor supports organisation-owned questions. Classification screens support exam groups, categories and subcategories, subjects, topics, subtopics and question sections through native create/update actions. Category edits preserve native group ordering and header/search metadata; no group selection means organisation-wide availability. Subcategories use native parent validation and inherit group availability from their parent; the native subcategory feature setting is enforced during saves. Category deletion and central language administration are not yet editable here. Classification draft restoration uses controlled revision checks, without independently restoring stale DOM field values. Feature restrictions for the existing native backend are retained, but are not evidence that each replacement internal screen is ready.

Same-domain student sign-in, staff-issued exam links, start/resume, answer saving, submission, published result history and staff pending-answer marking now have local implementations and tests. ExamElite's native controllers still own attempts and grading. The student and marking renderer supports bounded formulas and private question/passage/reference images; this does not provide a rich authoring editor or student answer uploads. See [current student and marking status](examelite-student-attempts.md) for exact boundaries. The full integration is not ready for deployment as a completed release.

The external native workspace browser path is retired in the local implementation. Public launch requests return 410 without contacting the provider, and the provider refuses non-provisioning launch requests. Its early host middleware rejects application requests on old `t4l-*.examelite.com` hosts, including requests carrying previously valid sessions or tickets. Ordinary ExamElite hosts and private central API calls remain available. Private provisioning still creates isolated mappings but never issues tickets or grants all exam groups to a student. These changes take effect only after the user deploys both sides; the assistant has not changed live sessions. Existing ticket/session tables are retained, but they cannot restore the retired browser path. Same-domain access continues to enforce module, feature and grant checks.

## Deployment and verification history

The milestones below record the sequence of implementation. Earlier statements that a student screen or marking is unavailable describe that milestone, not the current status above. Test counts are also historical; the latest repository check passes 85 tests, with native-controller and synthetic browser checks run separately.

Development and tests run locally. Live access by the assistant is read-only. The user runs `deploy/examelite/deploy-central-content.sh` from a checked Git revision. The script requires the earlier native provider setup, preserves private credentials, installs additive sources, adds `tech4learn_content_transfers` and `tech4learn_authoring_requests`, verifies routes/schema and updates Tech4Learn. It does not install certificates or create DNS records.

`npm run check` covers the scaffold. `test-content-api.php` runs against an isolated SQLite database using ExamElite model definitions and tests complete-selection tenant checks, no partial copy on a foreign selection, request replay and pull provenance. `test-content-copies.php` additionally tests destination ownership, original preservation, native settings/translations and retry preservation. The local browser preview uses synthetic questions and checks enable/share/pull controls; it is not a live data or full exam workflow test.

`test-question-authoring.php` invokes the installed native question controller against synthetic SQLite records. It checks answer preservation across multiple-choice, true/false, blanks and numerical rules, native validation, foreign references, stale edits, replay, rejected ownership/markup changes and request-context restoration. Local checks also use a read-only snapshot of the current live controller/models. Host resolution and identity infrastructure are test doubles; this is not a live authoring test. A synthetic browser check covers patch-only saving, revision/request identity, validation draft retention and HTML sanitisation.

Creation/classification verification additionally covers native question translation creation, create retries, the original five taxonomy kinds plus categories and subcategories, subject edit scope preservation, foreign taxonomy rejection and restricted writes. The synthetic browser creates a numerical question and a subject through the internal forms. These are local checks, not proof of a live deployment.

The installer also fixes the verified native ExamController create-action bug where `passing_percentage` was read from an unassigned `$validated` variable. The transformation assigns the existing native validation result, is idempotent, rejects an unrecognised controller shape, and participates in the installer backup/rollback. This does not make the internal exam builder complete.

The builder verification runs the current native ExamController against isolated SQLite records, including exact fractional pass thresholds, owned group/language scope, repeat creates, settings edits, question add/remove and mixed-tenant selection rejection. Queue dispatch, paper cache invalidation and the native permission helper are isolated test doubles; Tech4Learn permission enforcement has separate HTTP tests. The synthetic browser creates an exam with a fractional threshold and adds/removes a question using refreshed revisions. Native delivery flags are stored engine settings, not evidence that the corresponding student workflow is available inside Tech4Learn yet.

Paper controls now include native section create/update/removal, assignment through organisation question-section definitions, per-subject durations, and desired Active/Inactive status. Complete subject selections are validated against the owned paper; negative, missing and foreign timers are rejected before native writes. Revisions include question-section pivots and saved timers. Status requests use desired state plus the request ledger, so repeat activation cannot toggle an exam off. These controls do not yet expose student attempts.

Native tests cover section duration overflow, foreign sections, assignment revision changes, publication retries, timer scope/overflow and empty-section removal. The synthetic browser verifies activation, section creation/editing, subject timer values, fresh revisions and successful draft clearing. The full scaffold check remains 82 passing tests.

The [student attempt adapter components](examelite-student-attempts.md) now have local native tests for answer persistence, submission/deadline rejection, retries and student-safe payloads. They are private components with no new public/student route; student authentication, explicit exam grants and the full attempt UI remain outstanding.

Migration 15 and the student entry now implement separate exam-scoped sign-in, expiring grants and revocation without staff membership. The real HTTP and synthetic browser checks pass; full project verification now has 83 passing tests. The student page explicitly marks exam delivery unavailable until native start/resume/submission is connected, and grant-issuing controls are not yet exposed in the staff UI.

The latest local milestone replaces that delivery placeholder with a basic internal attempt screen and authenticated native start/resume, save and submit calls. It includes question navigation, explicit answer saving/clearing, review flags, countdown, lost-response retries and submission confirmation. Grant-derived identity is checked before and after engine calls; browser-supplied learner or paper overrides are rejected. Unsupported media/formulas and advanced delivery controls fail before committing a new attempt. Staff link issuance remains withheld, and this is not the complete exam integration release. See [current student workflow status](examelite-student-attempts.md).
